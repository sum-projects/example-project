# Domain model

## Ubiquitous language

| Term | Meaning |
| --- | --- |
| Lead | A person who showed interest and has not yet been confirmed as a sales opportunity |
| Source | Where the lead came from: `website`, `referral`, `event`, `cold_call`, `other` |
| Owner | The sales representative responsible for a lead or a deal |
| Contact (verb) | Record that the owner reached the lead for the first time |
| Qualify | Confirm the lead is a real opportunity and estimate its value |
| Disqualify | Close the lead as not worth pursuing, with a reason |
| Convert | Close a qualified lead by turning it into a customer with an open deal |
| Customer | A person or company the team is selling to, or has sold to |
| Deal | One sales opportunity with a customer, with a value and a stage |
| Stage | A deal's position in the pipeline |
| Win / Lose | Close a deal as successful or unsuccessful |

Code uses exactly these words. If a new concept appears, add it here first.

## Bounded contexts

| Context | Module | Responsibility | Aggregate |
| --- | --- | --- | --- |
| Lead management | `Leads` | The lead lifecycle up to conversion | `Lead` |
| Customer registry | `Customers` | Who the customers are | `Customer` |
| Sales pipeline | `Sales` | Deals and their progress | `Deal` |

Context map: `Leads` is upstream of `Customers` and `Sales`. Both consume the `LeadConverted` integration event published by `Leads` and translate it into their own model. No context reads another context's tables or classes; what one context may see of another is its `Contracts` (see the [architecture document](03-architecture.md#contracts)).

```
Leads ──LeadConverted──► Customers   (registers a customer)
      └─LeadConverted──► Sales       (opens a deal)
```

`Sales` stores only the `CustomerId` and never loads a `Customer`.

## Shared kernel

Kept minimal, in `Shared\Domain`:

- `AggregateRoot`: records domain events and releases them
- `DomainEvent`: marker interface with `occurredAt`
- `Uuid`-based identifier base class (UUID v7)
- `Email`: normalised to lower case, validated
- `Money`: integer amount in minor units plus ISO 4217 currency; immutable; arithmetic and comparison only within one currency
- `SalesRepId`: identifier of a sales representative
- `Clock`: interface for the current time
- Failure types: the base exceptions that every domain exception extends, each carrying a stable code (see [error handling](03-architecture.md#error-handling))

## Leads context

### Lead (aggregate root)

State: `LeadId`, `PersonName` (first and last name), `Email`, optional `CompanyName`, `LeadSource`, `LeadStatus`, optional owner `SalesRepId`, optional estimated value `Money`, optional `DisqualificationReason`, timestamps.

Status transitions:

| From | Operation | To |
| --- | --- | --- |
| (none) | `capture` | `New` |
| `New` | `markContacted` | `Contacted` |
| `Contacted` | `qualify` | `Qualified` |
| `New`, `Contacted`, `Qualified` | `disqualify` | `Disqualified` |
| `Qualified` | `convert` | `Converted` |

`assignOwner` is allowed in any non-terminal status and does not change the status.

Invariants:

1. `Converted` and `Disqualified` are terminal: no operation is allowed afterwards.
2. A lead can be marked contacted only if it has an owner.
3. Qualifying requires an estimated value greater than zero.
4. Disqualifying requires a non-empty reason (at most 500 characters).
5. Only a `Qualified` lead can be converted.
6. Assigning the current owner again is a no-op and records no event.
7. No two non-terminal leads share an email address. This is a set-based rule, so it is checked by the domain service `UniqueLeadEmailSpecification` (interface in Domain, implementation in Infrastructure) when a lead is captured, and backed by a partial unique index.

Any violated transition throws a domain exception that names the rule.

Domain events: `LeadCaptured`, `LeadOwnerAssigned`, `LeadContacted`, `LeadQualified`, `LeadDisqualified`, `LeadConverted`.

### Conversion

`Lead::convert(CustomerId, DealId, Clock)` receives the identifiers of the customer and the deal that will be created. They are generated by the application before the command is dispatched and are carried by the event, which makes downstream handling idempotent and lets the API return them immediately.

## Customers context

### Customer (aggregate root)

State: `CustomerId`, `PersonName`, `Email`, optional `CompanyName`, `CustomerStatus` (`Active`, `Archived`), origin `LeadId`, timestamps.

Operations: `registerFromLead` (factory), `archive`.

Invariants:

1. A customer is always registered with a name and an email.
2. Archiving an archived customer is rejected.

Domain events: `CustomerRegistered`, `CustomerArchived`.

## Sales context

### Deal (aggregate root)

State: `DealId`, `CustomerId`, title, value `Money`, `DealStage`, owner `SalesRepId`, optional `LossReason`, timestamps including `closedAt`.

Stages: `Discovery` → `Proposal` → `Negotiation` → `Won`, and `Lost` from any open stage.

| From | Operation | To |
| --- | --- | --- |
| (none) | `open` | `Discovery` |
| `Discovery` | `advance` | `Proposal` |
| `Proposal` | `advance` | `Negotiation` |
| `Negotiation` | `win` | `Won` |
| `Discovery`, `Proposal`, `Negotiation` | `lose` | `Lost` |

Invariants:

1. A deal's value is greater than zero.
2. `advance` moves exactly one stage forward; stages cannot be skipped or reversed.
3. Only a deal in `Negotiation` can be won.
4. Losing requires a non-empty reason.
5. `Won` and `Lost` are terminal.
6. The value can be changed only while the deal is open, and only within the same currency.

Domain events: `DealOpened`, `DealAdvanced`, `DealValueChanged`, `DealWon`, `DealLost`.

## Integration events

Integration events are the published language between contexts. They are separate classes from domain events, live in the publishing module's `Contracts\Event` namespace, contain only scalars, and are versioned by class name.

| Event | Published by | Payload | Consumers |
| --- | --- | --- | --- |
| `LeadConvertedV1` | Leads | `leadId`, `customerId`, `dealId`, `firstName`, `lastName`, `email`, `companyName`, `ownerId`, `estimatedValueAmount`, `estimatedValueCurrency`, `occurredAt` | Customers: register customer. Sales: open deal |

Consumers are idempotent: handling the same event twice finds the aggregate already created under the carried identifier and does nothing.

The deal's title defaults to `"<company or full name> - initial deal"`.

## Modelling rules

- Aggregates reference other aggregates by identifier only.
- One transaction changes one aggregate. Anything that spans aggregates is eventually consistent and driven by events.
- Value objects are immutable, self-validating, and compared by value.
- Enums model closed sets (`LeadStatus`, `LeadSource`, `DealStage`, `CustomerStatus`); transition rules belong to the aggregate or the enum, never to handlers.
- Time comes from `Clock`; the domain never calls `new DateTimeImmutable()` for "now".
