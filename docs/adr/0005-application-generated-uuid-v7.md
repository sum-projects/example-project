# 0005. Application-generated UUID v7 identifiers

Status: Accepted (2026-11-14)

## Context

Command handlers return nothing, yet the API must tell the client which resource was created. Lead conversion must also announce the identifiers of a customer and a deal that do not exist yet.

## Decision

Identifiers are UUID v7 values generated by the application (in the user interface layer, through an injected generator) before the command is dispatched, and passed in the command. Each aggregate has its own identifier value object.

## Consequences

- Commands stay free of return values; `201` and `202` responses can include identifiers immediately.
- Asynchronous consumers create resources under identifiers fixed in advance, which makes retries idempotent.
- UUID v7 is time-ordered, so primary key indexes stay compact compared with random UUIDs.
- Identifiers are longer than integers and not human-friendly.

## Alternatives considered

- **Database sequences.** Rejected: the identifier is unknown until after the insert, forcing commands to return data.
- **UUID v4.** Rejected: random ordering fragments indexes for no gain.
- **Client-supplied identifiers.** Rejected for now: requires extra validation and conflict handling on a public API.
